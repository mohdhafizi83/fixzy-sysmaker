Data Deletion Strategy

Marks records as deleted (e.g., using a `deleted_at` timestamp) but they remain in the database. This allows for easy data recovery but requires manual cleanup.

Permanently removes records from the database using `DELETE FROM...`. This action is irreversible and frees up database space immediately.

Core Modules

Authentication

The process of verifying who a user is. This module provides different ways for users to sign in to your application.

Authorization

The process of determining what an authenticated user is allowed to do. This typically involves user groups and permissions.

Log Audit

Records significant events in a log file or database table, such as user logins, data changes, and administrative actions for security and compliance.

Fake Data

Automatically populate your database tables with realistic-looking sample data. This is incredibly useful for testing, demonstrations, and learning how the application works without manual data entry.

Application Debugging

Enable detailed error reporting and display a developer debugbar at the bottom of the screen to monitor database queries, memory usage, and performance.
Warning: Never enable this in a live production environment as it may expose sensitive database passwords and API keys!

    Architecture & Multi-Tenancy

    All data resides in a single shared space. Access is controlled purely by Authentication and User Roles (Filament Shield). Best for standard portals and CMS.

    A user is strictly tied to ONE entity (e.g., one Faculty, Branch, or Department). Data is scoped automatically under the hood without needing a tenant switcher in the UI.

    A user can belong to MULTIPLE entities. Filament will generate a tenant switcher dropdown in the top navigation bar (SaaS style), allowing users to switch contexts.

            SQL Import Error Troubleshooting Guide

            The import process failed.

            This usually happens not because of a bug in FiziSysMaker, but because your SQL script contains advanced or vendor-specific syntax that cannot be translated. Our parser is designed to understand the core CREATE TABLE structure.

            What Should You Do?

            Please review and clean up your SQL script. Focus on keeping only the basic CREATE TABLE commands. Here is a checklist of items to remove:

            • Commands Other Than CREATE TABLE: Remove any commands such as CREATE VIEW, CREATE TRIGGER, CREATE PROCEDURE, or PARTITION BY clauses.
            • Complex Column-Level Clauses: Remove clauses like CHECK, CHARACTER SET, and COLLATE from individual column definitions.

              Example:

              Before (Complex):

              price DECIMAL(10,2) NOT NULL CHECK (price > 0) CHARACTER SET latin1,

              After (Simplified):

              price DECIMAL(10,2) NOT NULL,
            • Non-Standard Comments: While standard comments (-- or /* ... */) are safe, some database tools export proprietary metadata or comments. Please remove these.

            After cleaning up the script, please save it and try importing again.
